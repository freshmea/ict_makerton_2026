# 6개 버튼의 번호 음성과 count 비프음

후속 변경(2026-10-25): **SW2에도 SW1과 같은 4비프음 길게 누르기**를 적용했다. 즉시 “이번” → 0.8초 간격 비프음 4회 → 긴 비프음 후 GPT Decisions로 두 카메라 20장을 분석하고 음성·빛·서보 4개로 반응한다. 다시 길게 누르면 분석·반응을 취소한다. SW1은 Live, SW3~6은 기존 번호·비프음 기능을 유지한다. 아래의 SW2~6 설명은 번호 음원 공통 부분이며, 새 SW2 분석 실행과 비용·동시 실행 제한은 [Decisions 기기 반응](Decisions_학습분석과_기기반응.md)을 따른다.

2026-10-25 KST. **1번을 누르면 즉시 “일번” MP3를 재생한다.** 누른 상태를 유지하면 **0.8초** 간격으로 비프음이 올라가고, 네 번째 비프음까지 재생에 성공한 뒤 한 번만 Live를 시작한다. 짧게 눌렀다 떼면 번호만 안내하며 대화를 만들지 않는다. 시작 순서는 **“일번” → 짧은 비프음 4회 → “라이브 대화 시작” MP3 → 0.6초 긴 비프음 → Live API 연결**이다. 종료하려면 손을 떼고 다시 같은 방식으로 길게 누른다. 마이크 전송과 Live 출력을 중지하고 **“라이브 대화 끝” MP3와 긴 비프음**으로 알린다. 2~6번은 “이번·삼번·사번·오번·육번”과 상승 비프음을 사용한다.

## 실제 실행 위치

| 역할 | 실행 주체 | 소스 |
| --- | --- | --- |
| GPIO 입력, 30ms 디바운스, 누름·해제·count 생성 | Pico의 Rust 펌웨어, 5ms 샘플링 | `firmware/pico2-device-bench/src/main.rs`의 `touch_task`, `crates/pico-device-protocol/src/lib.rs`의 `TouchEngine` |
| USB 바이너리 이벤트 → JSON | Jetson의 Rust `pico-device-bench bridge`, 대시보드 자식 프로세스 | `tools/pico-device-bench/src/lib.rs` |
| 번호 음성·비프음 선택과 재생 작업 | Python `300seconds-dashboard.service` 안의 두 작업 스레드 | `apps/device-dashboard/button_audio.py`, `hardware.py`, `app.py` |
| 실제 스피커 PCM 출력 | 위 서비스가 실행하는 `aplay` 자식 프로세스, ALSA `robot_playback` | `hardware.Audio.play_feedback` |
| 처음 6개 번호를 합성 | 별도 Python `300seconds-tts.service` → Rust `nano-runtime typecast-sample` → Typecast | `tts_worker.py`, `build_button_audio.py`, `software/services/nano-runtime/src/typecast.rs` |

점검 당시 실행 중인 서비스는 대시보드·TTS·observer였다. 독립 Rust `audiod` 서비스는 실행되지 않았다. 시스템 서비스는 Python으로 실행되지만 USB 브리지와 TTS 제공자 호출에는 Rust 프로그램이 사용된다. 새 버튼 기능은 서버에서 자동 시작하며 브라우저 실행과 무관하다. 대시보드 systemd 서비스를 정지하면 버튼 소리도 정지한다.

현재 설치된 Pico 펌웨어가 이미 필요한 `Pressed`, `Interval`, `Released`, `WindowClosed` 이벤트와 순번을 제공한다. 해당 엔진에 6개 입력의 계약 검사를 추가했으며 바이너리나 전기 배선은 변경하지 않았다. Pico에 MP3 디코더나 스피커 출력 배선을 추가한 구성이 아니다.

## 음원과 재생

- 영구 캐시: `/var/lib/300seconds-dashboard/button-audio/button-1.mp3`~`button-6.mp3`
- `button-1.mp3`는 누를 때 즉시 안내하는 “일번”이다. 시작 문구는 별도 `live-start.mp3`, 종료 문구는 `live-end.mp3`이다.
- 저장소 및 배포 묶음: `apps/device-dashboard/assets/button-audio/`
- `button-N.wav`: 해당 MP3를 미리 디코딩한 48kHz/16bit/mono PCM. 버튼을 누를 때 파일 변환을 반복하지 않는다.
- `manifest.json`: 문구, 재생 시간, MP3·WAV 각각의 SHA-256. 시작 시 모두 확인한다.
- `BUTTON_AUDIO_DIR`를 지정하면 캐시 위치를 바꿀 수 있다. 기본 영구 캐시가 없으면 배포에 포함된 음원을 사용한다.

음성은 기존 Typecast 목소리로 합성한 결과다. 1~6번은 숫자의 고유어 해석을 피하도록 한글 문구로 고정했고, Live 시작·종료 안내는 별도 파일로 저장했다. 각 파일의 길이는 manifest에 기록한다. 합성 후 앞뒤 무음을 정리하고 원본 PCM peak를 -9dBFS로 맞춘 뒤 MP3로 저장했다. 이후 음성은 MP3에서 디코딩한 캐시로만 재생한다. 안내 음성·비프음 재생에는 API 요청·인터넷 연결이 필요 없으며 실제 Live 대화는 유료 API를 사용한다.

비프음은 80ms 사인파이고, 시작·끝에 20/25ms 완만한 페이드를 적용한다. peak는 -24dBFS이다. 음높이는 `440 × 2^((count-1)/24)`Hz로 반음의 절반씩 오르며, count 39부터 약 1,318.51Hz에서 고정한다. 여러 버튼의 비프음이 동시에 대기하면 섞어서 재생하고 peak가 커지지 않도록 평균한다.

## 이벤트와 GPT Live 공존

USB 소유자의 이벤트 콜백을 사용한다. 화면의 마지막 이벤트를 주기적으로 읽는 방식은 짧거나 동시에 발생한 버튼 입력을 잃을 수 있어 사용하지 않는다. USB 세션과 32bit 이벤트 순번, 장치 시각 및 호스트 시각을 확인해 중복·오래된 입력을 거른다. 재연결 시 대기열과 누름 상태를 비우며, 새 `Pressed` 없이 들어온 기존 hold의 `Interval`을 재생하지 않는다.

SW1의 기존 누름 즉시 Live 토글 코드는 제거했다. 새 `Pressed`에 고유 토큰을 부여하고 “일번”과 count 1~4의 비프음이 각각 성공한 뒤에만 Live 요청을 만든다. 네 번째 비프음 재생 중에는 요청을 만들지 않으며, 같은 버튼의 여러 count를 한 소리로 합치지 않는다. 재생 누락·실패 시 연결하지 않는다. 손을 뗄 때까지 다시 요청하지 않으며, 새 누름·USB 세션의 음성과 이전 입력을 혼동하지 않는다. 고정 2초 창의 `WindowClosed`는 길게 누름의 확인 상태를 해제하지 않는다. 시작 안내와 긴 비프음이 모두 성공한 뒤 대화 DB 행과 API 세션을 생성한다. 음원 누락·재생 실패·안내 중 취소·USB 세션 변경 시 시작을 중단한다. 종료 요청 시 마이크 전송을 멈추고 재생 중이던 Live 출력 프로세스를 종료한 뒤 종료 안내를 재생한다. 대시보드 종료·10분 타이머·연결 종료에도 종료 안내를 한 번만 재생한다.

음성·비프음 대기열은 각각 12개까지이다. 혼잡하면 오래된 항목을 버리고, 번호는 3초·비프음은 0.75초가 지난 항목을 재생하지 않는다. 정상적인 단일 버튼의 0.8초 count에는 충분한 처리 여유가 있다. 과도한 연타·전송 지연 시 과거 소리를 길게 밀려 재생하는 대신 해당 항목을 버린다.

ALSA `robot_playback`을 같은 사용자끼리 공유하는 `robot_dmix`로 연결했다. 설정 파일은 `/etc/alsa/conf.d/99-300seconds-usb.conf`이며 설치 원본은 `tools/jetson/device_access.py`이다. 캡처와 시스템 기본 PCM 설정은 그대로이다. 모든 대시보드 재생은 `boarddash` 계정으로 실행한다. 일반 TTS·시험 재생·GPT Live 사이의 기존 재생 잠금은 유지하고 버튼 피드백만 혼합 출력한다.

버튼 소리가 나는 동안과 이후 0.25초 동안 GPT Live의 마이크 전송을 무음으로 바꿔 자체 번호·비프음이 발화로 들어가는 것을 줄인다. 이 구간 새로 받는 Live 출력 PCM은 25%로 감쇠한다. 이미 ALSA에 보낸 음성은 소급 감쇠하지 않는다.

## 운영과 확인

`GET /api/status`의 `button_audio`에 `ready`, 캐시 번호, 누름·count 수신 수, 실제 재생 성공 수, 폐기·거절 수, 마지막 오류와 음높이가 나온다. `live_hold_count=4`, `live_hold_ms=3200`, `live_hold_requests`, `announcing`, 현재 누름에서 성공한 비프음 수 `sw1_beeps_played`도 확인할 수 있다. `ready=true`는 버튼 음원 6개와 별도 시작·종료 음원 및 PCM 캐시의 무결성이 확인됐다는 뜻이며 물리적인 청감 확인을 뜻하지는 않는다. `Audio.play_feedback`은 ALSA 성공 여부를 검사한다.

기존 음원을 재사용하려면 파일을 그대로 배포한다. 새 합성이 필요할 때만 다음을 실행한다. 완료된 manifest 항목은 재합성하지 않으며, 기존 파일의 체크섬이 달라지면 중단한다. 합성에는 기존 Typecast 문자·크레딧 한도가 적용된다.

```bash
cd /opt/300seconds/dashboard/app
sudo -u boarddash env HOME=/var/lib/300seconds-dashboard \
  /opt/300seconds/dashboard/venv/bin/python -B build_button_audio.py \
  --output /var/lib/300seconds-dashboard/button-audio
sudo systemctl restart 300seconds-dashboard
```

설치된 서비스가 이미 사용 중인 ALSA 장치의 구성을 바꿀 때는 대시보드를 정지하고 설정을 교체한 뒤 시작한다. 시스템 전역의 다른 오디오 데몬이나 다른 계정으로 같은 USB 장치를 직접 열면 공유할 수 없는 경우가 있으므로 장치 소유자를 먼저 확인한다.

최초 검증 기록은 [검증 폴더](dashboard-check/2026-10-25/button-audio/)에 있으며, 0.8초·한글 번호 음원 교체는 [추가 검증](dashboard-check/2026-10-25/button-audio-tuning/)에 기록했다. 4카운트 제어 도입은 [안전 조작 검증](dashboard-check/2026-10-25/button-live-hold4/), 현재의 즉시 번호 안내와 비프음 4회 완료 조건은 [최신 검증](dashboard-check/2026-10-25/button-live-number-first/)에 기록했다. 실제 버튼 누름의 최종 청감은 사용자가 각 버튼을 눌러 확인할 수 있다. 자동 시험은 물리 GPIO를 조작하지 않는다.
