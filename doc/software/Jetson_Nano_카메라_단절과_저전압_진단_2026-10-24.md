# 카메라 단절·재등장과 속도 저하 재진단

2026-10-24 **14:38~14:41 KST**. 사용자 요청으로 읽기 점검과 짧은 MJPEG 수신 시험만 수행했다. 펌웨어, 전원 모드, 카메라 프로필, 서비스 설정을 변경하거나 서비스를 재시작하지 않았다. AI API 호출도 없다. 수신 시험은 종료했다.

## 확인된 상황

**Nano 전체 재부팅은 없었다. 전원 입력 저전압, 카메라 서비스의 과거 충돌, 최근 대시보드 재시작, 5W 모드에서의 높은 CPU 부하가 함께 확인됐다.** 이전 현장 진단 때의 큰 무선 지연은 이번 표본에서 재현되지 않았다.

NVIDIA는 Nano 모듈에 최소 **4.75V**가 필요하다고 안내하며, 부하가 큰 개발 키트에는 **5V·4A DC 입력**을 권장한다. 현재 보드 센서값은 이 하한보다 낮다. [NVIDIA 전원 안내](https://forums.developer.nvidia.com/t/power-supply-considerations-for-jetson-nano-developer-kit/71637). 입력 센서 경로와 mV 단위는 [해당 Nano 측정 사례](https://forums.developer.nvidia.com/t/power-supply-considerations-for-jetson-nano-developer-kit/71637/271)와 일치한다. 전압 강하·보호 동작과 OC 경고의 관계는 [NVIDIA 담당자의 보호 기구 설명](https://forums.developer.nvidia.com/t/system-throttled-due-to-over-current/158055/3)을 참고한다. 이 보드의 특정 어댑터·케이블·컨버터 중 무엇이 원인인지는 아직 구분하지 못했다.

## 속도가 줄어드는 구간

| 단계 | 카메라 1 / SENSOR 0 | 카메라 2 / SENSOR 1 |
| --- | ---: | ---: |
| 센서 수신·H.264 생성 | 약 30fps | 약 30fps |
| 웹 JPEG 생성 | 약 15fps | 약 15fps |
| 노트북 MJPEG 수신 | **11.14fps** | **11.18fps** |
| Nano 내부 동일 HTTP 수신 | **10.97fps** | **11.03fps** |

각 수신 표본은 6초다. 기존 시청자를 유지한 채 진단 클라이언트를 추가했으며 로컬·노트북 비교는 약 2분 간격으로 수행했다. 두 시험의 camera run ID는 동일했다. 브라우저 그리기·노출부터 표시까지의 전체 지연은 측정하지 않았다.

현재 Nano→공유기 ping 평균 **2.744ms**, PC→Nano 평균 **5ms**, 손실 0%. TCP 송신 큐도 확인 순간 0이었다. Nano는 이전 정상화 때와 같은 2.4GHz 채널 6/BSSID에 연결되어 있다. 따라서 **이번 15→11fps 감소는 무선 이전의 웹 스트림 제공 경로에서도 발생**한다. 이전 약 3fps·수백 ms의 무선 병목을 현재 원인으로 그대로 적용할 수 없다. 현장의 다른 시각에 무선 혼잡이 재발할 가능성은 별개다.

코드에서 각 MJPEG 연결이 상태 JSON·JPEG를 반복 읽고 전송한 뒤 `sleep(1/15)`한다. 처리·스케줄링 시간이 이 대기에 더해져 실제 간격이 길어지고 프레임을 건너뛸 수 있다. 현재 노트북 프레임 수신 간격은 평균 약 89~90ms, 최대 250ms다. 높은 CPU 부하는 이 감소와 부합하지만, CPU·폴링·저전압 보호 동작 각각의 기여도는 통제된 비교 시험으로 분리하지 않았다. 클럭 921MHz와 코어 2개는 현재 5W 설정으로도 설명되므로 전부 보호 스로틀링의 결과로 단정하지 않는다.

또한 두 카메라가 하나의 GStreamer 파이프라인을 사용하며 ERROR 발생 시 전체 worker가 종료된다. 대시보드가 해당 worker의 부모이므로 대시보드 재시작도 두 영상을 함께 재시작한다. 현재 코드는 자동 재연결 감독이 없어 Argus만 회복돼도 영상 worker가 저절로 복구된다는 보장이 없다.

## 권장 대안과 검증 순서

1. **전원 경로를 먼저 해결한다.** Nano 전용 안정화 5V·4A 전원, 짧고 충분한 굵기의 케이블·커넥터, DC 입력 선택 점퍼 및 주변 장치 전원 분리 상태를 확인한다. 실제 연결 중인 전원 방식은 현물 확인이 필요하다. 현재 카메라 부하에서 보드 입력이 4.75V 이상으로 유지되고 OC 경고가 사라지는지 대조한다. 단순히 어댑터 정격이 5V·4A라는 표시만으로 확인을 끝내지 않는다.
2. **현장 임시 운용은 처리량을 줄인다.** 중복 대시보드 탭을 닫고 필요한 한 카메라만 미리본다. 웹 미리보기 목표를 5~10fps로 낮추는 설정을 추가하면 CPU·트래픽을 줄이는 대안이 된다. 학습 분석은 기존대로 보드의 최신 사진을 1초마다 읽으므로 매끄러운 웹 영상과 별도다. 현재 `360p` 촬영 프로필을 골라도 JPEG 미리보기는 640×360으로 고정되므로 웹 부하가 같은 비율로 줄어든다고 약속할 수 없다.
3. **전원이 안정된 후 성능 모드를 비교한다.** 5W와 MAXN/10W의 실제 CPU·수신 FPS·전원 경고를 비교한다. 지금 저전압 상태에서 최대 클럭을 강제로 올리는 방식은 채택하지 않는다. 본 진단에서 전원 모드를 변경하지 않았다.
4. **소프트웨어는 카메라 수명 주기를 분리한다.** 카메라 worker를 별도 서비스로 두고 프레임 정지 감시·횟수 제한·점진 대기로 복구한다. 대시보드/USB/Pico 작업과 영상 재시작을 분리하고, 가능하면 센서별 오류도 격리한다. 전원 안정화 후에도 특정 센서의 CSI 오류가 반복되면 전원을 끈 상태에서 케이블·커넥터를 점검하고 센서별 단독 시험으로 원인을 나눈다.
5. **매끄러운 실시간 영상은 기존 H.264 RTSP를 비교한다.** `rtsp://192.168.184.76:8554/cam0`는 이미 약 30fps H.264를 생성하고 있다. VLC 등으로 비교하면 MJPEG 웹 제공 경로를 우회할 수 있다. 이번에는 RTSP 실수신 시험을 추가하지 않았다. 브라우저 내부 30fps가 필요하면 WebRTC 등의 연결 계층 구현을 별도로 검토한다. 유선 Ethernet은 향후 무선 변동을 줄이는 대안이지만 이번 11fps 감소를 단독으로 해결할 것으로 보장하지 않는다.

현재 두 카메라는 ready이며 API·Pico·마이크도 정상 응답했다. 서비스나 전원 설정을 변경하지 않고 진단을 종료했다.
