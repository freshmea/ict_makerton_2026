# 카메라 지연 현장 진단

2026-10-24 KST, 메이커톤 현장. Nano `192.168.184.76`, 노트북 `192.168.184.82`, 공유기 `192.168.184.1`. 노트북 영상 수신 측정 시작은 **11:45:12 KST**, 사용자 승인 후 Nano 내부 영상 수신 측정 시작은 **11:52:27 KST**다.

**13:00 KST 재측정에서는 영상 수신이 약12.4fps로 회복됐다. 연결 BSSID와 채널도 달라졌다.** 아래 초기 진단은 느렸던 시점의 기록이며, 정상화 비교는 문서 뒤에 추가했다.

## 확인된 병목

**주 병목은 Nano가 연결된 2.4GHz 무선 경로와 영상 전송 대기열이다.** 촬영·인코딩은 약30fps, JPEG 생성은 약15fps로 유지됐다. 동일한 HTTP 경로를 Nano 내부에서는 두 채널 각각 12.89fps·12.54fps로 받지만, 노트북 진단 클라이언트에서는 3.05fps·2.80fps로 수신했다. Nano→공유기 ping도 평균596.9ms로 느리다. 브라우저 디코딩·화면 그리기를 하지 않는 수신기에서도 발생하므로 브라우저 표시 단계 이전에 병목이 존재한다. RF 혼잡·간섭, AP의 대역폭 정책, 드라이버 문제 중 최종 원인은 아직 분리하지 못했다.

## 전송 지연의 실제 영향

진단 수신기 두 개가 동작할 때 JPEG 한 프레임 수신 간격은 평균 328ms / 357ms, 최대 969ms였다. 화면에 움직임이 뚝뚝 끊겨 도착할 수 있는 간격이다. 첫 완전한 프레임까지 약 2.5초가 걸렸다. 이 값은 연결 시작부터 첫 JPEG 수신까지이며 **노출부터 화면 표시까지의 지연 측정은 아니다.**

추가 영상 수신기가 없는 baseline에서도 작은 `/api/health` 응답이 평균 1,344ms, `/api/status` 응답이 평균 2,754ms 걸렸다. 두 영상을 추가로 받을 때 각각 평균 2,172ms와 5,907ms로 늘었다. 카메라 영상만의 문제가 아니라 상태 조회도 같은 통신 경로의 영향을 받는다.

JPEG 크기와 생성률로 계산한 두 채널 한 세트의 영상 데이터 요구량은 대략 **3.5~3.9Mbps**다. 진단기의 두 채널 실제 수신량은 합계 약 **0.69Mbps**였다. 이는 해당 연결에서 받은 JPEG payload 속도이며, Wi-Fi 전체 최대 용량을 측정한 값은 아니다. 기존 시청자가 더 있으면 영상 데이터 전송량도 추가된다.

## SSH 승인 후 내부 비교와 무선 상태

사용자가 현재 채팅에서 **SSH 읽기 점검을 승인**한 뒤, 기존 동일 보드 계정으로 접속하고 호스트 키 SHA-256을 기존 검증값과 대조했다. 서비스·프로필·네트워크 설정을 바꾸지 않았으며, 원격 진단 코드는 메모리에서 실행하고 결과 파일은 PC에만 저장했다.

- Nano: SSID `1_PCU_C`, **2.462GHz / 채널11**, `r8188eu` USB 드라이버. 드라이버가 보고한 링크 속도는72.2Mbps다. 이 수치는 실제 영상 전송량이 아니다.
- 노트북: SSID `1_PCU_C-owe-tr`, **5GHz / 채널36**, 보고된 링크 속도573.5Mbps. 두 장치는 같은 IP 서브넷이지만 서로 다른 무선 대역·BSSID에 연결돼 있다.
- Nano의 드라이버 절전 `rtw_power_mgnt=0`, `rtw_ips_mode=0`, `rtw_enusbss=0`, USB `power/control=on`, WEXT `Power Management:off`다. **현재 내부 절전이 켜져 있어서 느리다는 가설을 지지하지 않는다.** 새 Wi-Fi 프로필의 NetworkManager powersave 값은 `default`이지만 드라이버 런타임 값을 별도로 확인했다.
- `iwconfig`·`/proc/net/wireless`의 신호는100/100으로 표시된다. 반면 `iw dev wlan0 link`는 `Not connected`를 반환했다. IP 통신과 WEXT 연결은 실제로 동작하므로, 이 드라이버의 해당 신호·nl80211 보고만으로 RF 품질이나 연결 단절을 확정하지 않는다. `/proc/net/rtl8188eu` 등 예상 경로의 상세 드라이버 통계도 제공되지 않았다.
- RX dropped는 누적1,340개였으나 누적 시간과 증가율을 따로 측정하지 않았다. 현재 무선 패킷 손실률 또는 간섭의 증거로 단정하지 않는다.

Nano 내부에서도 서비스의 **동일한 LAN bind 주소**를 사용했다. `ip route get 192.168.184.76`은 `local ... dev lo`를 반환하므로, 이 비교는 Wi-Fi를 거치지 않는다. 12초 동안 두 채널155/151프레임을 받았고, 첫 JPEG까지85/77ms였다. 로컬 `/api/health` 평균35ms, `/api/status` 평균59ms였다. 이는 노트북 쪽의 수초 단위 응답과 명확한 차이다. 로컬도 생성 속도15fps에는 미달하므로 HTTP 폴링·스케줄링 부하에 따른 추가 손실은 존재하며, 전체 원인을 네트워크 하나로 배타적으로 설명하지 않는다. 두 비교는 약7분 간격이며 동일 시각 대조군은 아니다.

## TCP 전송 대기열

추가 진단 영상 연결을 닫은 뒤에도 노트북으로 향하는 기존 대시보드 연결3개가 남아 있었다. 두 대용량 연결의 `ss -tin` 결과는 다음과 같다. URL과 브라우저 표시 FPS를 소켓 통계만으로 식별하지 않았으므로, 두 연결을 실제 시청 중인 카메라라고 단정하지 않는다.

무선 경로가 지연되는 동시에, 생성된 영상 데이터가 송신 대기열에도 남는 양상이다. 이는 끊김과 늦게 따라오는 영상의 원인이 될 수 있다. 다만 이 큐 크기를 촬영부터 표시까지의 실제 지연으로 환산하거나, AP 내부의 큐 위치·혼잡 원인을 특정하지 않는다. TCP·장치 큐 누적이 지연을 늘릴 수 있다는 해석은 [Linux 커널 네트워크 문서](https://docs.kernel.org/networking/ip-sysctl.html)의 `tcp_limit_output_bytes` 설명과 부합하며, RTT 필드의 의미는 [ss 매뉴얼](https://man7.org/linux/man-pages/man8/ss.8.html)을 따른다. 현재 커널에 특정 최신 설정이 적용돼 있다는 뜻은 아니다.

**사용량 증가에 따른 일시적 혼잡은 가능한 설명이지만, 그것만을 원인으로 확정할 수 없다.** 같은 SSID에서도 연결된 BSSID와 채널이 바뀌었다. 다른 무선 접속점으로의 재연결/로밍, AP의 채널·운영 변경 등이 관여했을 수 있으며, 어느 동작으로 BSSID가 바뀌었는지는 로그로 확인하지 않았다. 카메라 worker와 프로필은 동일했고 CPU 평균도 낮아지지 않았는데 수신 성능은 회복됐다. 따라서 이번 속도 변화는 카메라 프로필·프로세스 변경보다 **외부 무선 경로의 조건 변화**와 부합한다. 앞선 측정과 현재 측정은 다른 시간대의 짧은 표본이다.

같은 무선 채널을 사용하는 장치의 실제 트래픽이 많으면 전송 기회 경쟁으로 지연이 커질 수 있다. 단순 접속자 수만으로 혼잡을 판단할 수는 없고 **채널 점유율, AP별 송수신 트래픽, 간섭·재전송률**이 필요하다. 이 구분은 [Cisco 공식 Wi-Fi 처리량 진단 문서](https://www.cisco.com/c/en/us/support/docs/wireless/catalyst-9800-series-wireless-controllers/221766-validate-wi-fi-throughput-testing-and.html)의 공유 매체·채널 점유율 설명을 따른다. 현장 AP가 Cisco 제품이라는 뜻은 아니다.

## CPU·온도 및 화면 수치의 의미

상태 표본에서 보드 CPU 평균은 baseline 70.05%, 한 채널 추가 67.00%, 두 채널 추가 64.85%였고 온도는 모두 50°C였다. CPU 부하는 높지만 촬영·인코딩·JPEG 출력 속도가 유지됐다. 이 표본만으로 CPU 부하가 네트워크 지연의 원인이라고 확정할 수 없다. CPU 클럭·전원 경고·프로세스별 부하는 별도 내부 점검 대상이다.

화면의 큰 FPS 숫자는 [app.js](../../apps/device-dashboard/static/app.js)의 `cam.fps`, 즉 보드 쪽 촬영 FPS다. Preview 숫자도 보드 내부 JPEG 생성 속도다. **노트북의 실제 수신·표시 FPS를 측정하는 숫자가 아니므로, 화면에 30fps가 보여도 영상이 느릴 수 있다.** 웹 영상 자체는 [media_worker.py](../../apps/device-dashboard/media_worker.py)와 [app.py](../../apps/device-dashboard/app.py)에서 최대 15fps로 제한된다. 30fps 촬영 설정을 높여도 현재 전송 병목은 해소되지 않는다.

## 확정한 범위와 남은 구분

- 확정: Nano 내부보다 노트북 수신이 크게 느리며, Nano→공유기에서도 평균약597ms 지연이 발생한다. TCP 송신 큐에도 데이터가 남아 있다. Nano의 현재 연결은2.4GHz 채널11이고 드라이버 내부 절전은 꺼져 있다.
- 주 병목: Nano가 사용하는 무선 경로와 외부 영상 전송. 로컬 HTTP 처리에도15fps를 모두 전달하지 못하는 부하가 있지만, 큰 전송 성능 차이를 확인했다.
- 미확정: 무선 혼잡/간섭, USB Wi-Fi 드라이버, AP 전달·대역폭 정책 중 세부 원인. 신뢰할 수 있는 RF 신호·재전송률과 무선 무부하 비교가 없다. 보드 스케줄링·전원 문제도 이번 승인 범위에서는 직접 조사하지 않았다.
- 미측정: 실제 브라우저 paint FPS, 촬영부터 화면까지의 전체 지연, 현장 유선 연결 결과, 현재 조건과 동일한 집에서의 대조군.

기존 집 환경의 [검증 기록](Jetson_Nano_장치_대시보드.md)은 기준 참고이며, 이번 측정과 동일 시각·부하의 비교군은 아니다. 장소가 바뀐 사실만으로 RF 간섭을 확정하지 않는다.

## 다음 비교 측정

1. 가능하면 Nano를 유선 LAN에 연결하고 같은 도구로 재측정한다. 현재 대시보드는 특정 IP에 bind되므로, 새 인터페이스를 사용하려면 주소 반영이 필요하다. 유선으로 ping·수신 FPS가 회복되는지 확인하면 무선 경로의 인과관계를 더 검증할 수 있다.
2. 모든 외부 영상 미리보기를 잠시 멈춘 대조군에서 Nano→공유기 ping을 비교한다. ping도 크게 회복되면 영상 부하와 큐 누적의 관계를 더 확인할 수 있다. 이번 승인 범위는 읽기 검사여서 기존 브라우저 연결은 임의로 닫지 않았다.
3. 현장 AP의2.4GHz 채널 혼잡·클라이언트별 대역폭 제한을 확인하거나, 별도 네트워크에서 같은 비교를 수행한다. 설정을 바꾸기 전에 무부하/영상 부하 결과를 남긴다.

SSH 검사는 처음 자동 승인 검토에서 인증 정보의 재사용이 거부됐지만, 사용자가 현재 대화에서 승인한 뒤 위 읽기 검사를 완료했다. 이번 진단에서는 서비스·프로필·네트워크 설정을 바꾸지 않았다.

## 재현 도구

새 도구 [measure-camera-delivery.py](../../tools/jetson/measure-camera-delivery.py)는 Python 표준 라이브러리만 사용하며 카메라·Pico·오디오 제어 명령을 보내지 않는다. 상태 API를 주기적으로 읽으면서 baseline → MJPEG 한 채널 추가 → 두 채널 추가를 측정한다.

```powershell
python tools/jetson/measure-camera-delivery.py --url http://192.168.184.76:8000 --seconds 12 --output tmp/camera-delivery-recheck.json
```

baseline은 **도구가 추가한 영상 연결이 없는 상태**를 뜻한다. 기존 브라우저·다른 참가자 연결은 닫지 않았으며, single/dual도 각각 진단 연결 1개/2개가 추가된 상태다. 도구는 JPEG 수신 시각·크기·동일 payload 개수만 기록하고 영상 이미지는 저장하지 않는다. 소켓 무응답 제한은 4초지만, 데이터가 조금씩 계속 도착하면 한 단계의 실제 벽시계 시간이 지정 시간보다 길어질 수 있다. `--help`, Python 구문 검사와 실제 현장 3단계 측정을 완료했다.
