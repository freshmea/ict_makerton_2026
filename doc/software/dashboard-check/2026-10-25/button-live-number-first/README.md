# SW1 즉시 “일번” 안내와 네 번째 비프음 완료 후 Live 시작

2026-10-25 KST. 1번을 눌렀을 때 번호가 들리지 않던 동작을 수정했다.

- 짧게 누름: 즉시 저장된 “일번” MP3를 재생한다. Live는 시작하지 않는다.
- 길게 누름: “일번” → 0.8초 간격 비프음 4회 → “라이브 대화 시작” → 0.6초 긴 비프음 → 연결.
- 네 번째 비프음 재생 중에는 Live 요청을 만들지 않는다. 번호와 count 1~4의 비프음이 모두 성공한 후에만 요청한다. 누락·재생 오류가 있으면 연결하지 않는다.
- 각 누름마다 새 토큰을 부여해 이전 입력과 새 입력의 완료 결과를 섞지 않는다. 같은 버튼의 count 여러 개를 하나의 비프음으로 합치지 않는다.
- 계속 누르고 있어도 반복 토글하지 않는다. 종료도 손을 떼고 새로 같은 길게 누르기 동작을 사용한다.

음원은 `button-1.mp3` = “일번”, `live-start.mp3` = “라이브 대화 시작”, `live-end.mp3` = “라이브 대화 끝”으로 분리했다. “일번”만 새로 합성하고 나머지 음원은 이전 파일의 문구·SHA-256을 확인해 재사용했다. [합성 로그](synthesize.log).

## 검증

- 로컬 관련 오디오 검사 34개 통과. Nano의 버튼·오디오·Live 수명주기 검사 **42개 통과**: [targeted-tests.log](targeted-tests.log).
- 네 번째 비프음의 완료를 대기시키는 검사에서, 완료 전에는 Live 요청이 없고 완료 후에 한 번만 생성됨을 확인했다.
- 실제 Nano ALSA 스피커와 생산 `ButtonAudio`·`Learning`·`Live` 코드로 짧은 누름, 시작, 지속 누름, 종료를 시험했다. 입력 이벤트는 시험용이며 GPIO를 물리적으로 누르지는 않았다.
- 순서는 “일번 + 비프음 3회”에서 세션 없음, 다음 누름의 “일번 + 비프음 4회 + 시작 안내 + 긴 신호음”에서 연결, 새 누름의 “일번 + 비프음 4회 + 종료 안내 + 긴 신호음”에서 종료였다. 번호 안내 3회, count 비프음 11회, Live 요청 2회이며 폐기·오류가 없었다.
- 최초 누름부터 `aplay` 실행 함수 진입까지 0.8ms였다. 이는 내부 재생 요청 지연으로, 스피커에서 소리가 들리기까지의 전체 지연을 측정한 값은 아니다.
- 가짜 Live 응답·임시 DB를 사용했다. 외부 Live API 호출 0회, 운영 대화 기록은 **전 6건 / 후 6건**으로 유지됐다. [검증 JSON](verification.json), [스피커 검증 로그](speaker-verification.log).
- 실제 Pico 설정은 800ms, 제어 조건은 4회, 준비된 MP3와 PCM은 8쌍이다.

초기 전체 검사에는 이전 DB 버전 2를 기대하는 오래된 설치 검사와 누락된 `test_observer_api` 모듈이 있었다. 현재 Nano는 별도 작업으로 DB 버전 3이 배포돼 있으므로, 이번 버튼 변경은 관련 검사 42개와 실제 출력 순서로 검증했다. 이 작업에서 관찰 DB·분석 코드나 Live 제공자 코드는 변경하지 않았다. [초기 검사 로그](nano-tests.log).

변경 파일: `button_audio.py`, `build_button_audio.py`, `test_button_audio.py`, 음원 및 운영 문서. 배포 중 대시보드를 재시작하고 연속 관찰 설정을 복원했다. 이전 앱·음원·DB 백업: `/var/lib/300seconds-dashboard/backups/button-live-number-first-20261024T180932Z`. [배포 기록](deployment.json).
