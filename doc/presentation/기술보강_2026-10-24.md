## 기술 설명의 기준

### Rust·Embassy와 RTOS

펌웨어는 `#![no_std]`, `#![no_main]`이며 RP2350 Cortex-M33 단일 코어의 `embassy_rp::executor::Executor`를 사용한다. Cargo에서 Rust 1.90, `embassy-rp`·`embassy-executor` 0.10.0을 고정했다. 정적 태스크·타이머·Channel·Signal·인터럽트/DMA로 운영체제의 태스크·시간 관리 역할을 구성한다. 현재 코드는 같은 executor 안에서 await로 협력 실행하므로 선점형 RTOS의 우선순위·최악 응답 시간을 보증하는 것으로 설명하지 않는다. 긴 동기 함수는 다른 태스크를 지연시킬 수 있다. [고정 버전 Executor 공식 문서](https://docs.embassy.dev/embassy-executor/0.10.0/cortex-m/index.html), [Embassy Book](https://embassy.dev/book/).

`main`이 `usb_task`, `rx_task`, `tx_task`, `touch_task`, `safety_task`를 spawn하고 `device_task`를 await한다. 장치별로 모든 출력을 독립 태스크에 분산했다는 초기 계획 대신, **PCA·양손 LED·눈 출력은 device_task 한 곳이 소유**한다. `COMMANDS=8`, `LOCALS=2`, `RESPONSES=8`, `EVENTS=16`의 유한 큐를 사용한다. 이벤트가 가득 차면 송신 대기 때문에 제어를 막지 않고 누락 수를 기록한다.

### SBC의 MA

여기서 MA는 저장소의 **Rust micro-architecture**를 뜻한다. `nano-runtime serve ROLE`이라는 같은 실행 파일을 역할별 독립 프로세스 7개로 운영한다. 구름 서비스형 MSA 전체나 7개 스레드로 표현하지 않는다. `controllerd`는 요청·정지·epoch·lease, `picod`는 USB, `camerad`는 두 CSI, `audiod`는 USB 오디오 입출력을 소유한다. `visiond`가 최신 프레임과 OCR 후보를 처리하고, `memoryd`가 SQLite WAL의 확인된 메모를 관리하며, `dialogued`가 ASR·외부 AI·TTS·동의·비용·취소를 연결한다.

SBC는 Rust/Tokio 1.48 기반이며 설치된 GStreamer·SQLite·CUDA를 작은 C ABI로 연결한다. 일부 로컬 AI worker도 사용하므로 모든 네이티브 라이브러리를 순수 Rust로 재구현했다는 설명은 피한다. runtime과 장치 진단 대시보드는 장치 점유가 충돌하는 별도 운영 경로다. 문서 안의 과거 서비스 상태보다 실제 운용 전 상태 확인을 우선한다.

### 초기 설계와 실제 실행판

| 항목 | 실제 구현과 설명 |

| MCU 무선 | Pico 2 W를 사용하지만 이번 펌웨어는 USB 제어만 사용 |

### USB와 하위 버스

```text
응용 메시지: Hello / KeepAlive / Arm / SetPose / SetLight / SetEyes / Stop
공통 타입: Frame { version:u8, session:u64, seq:u32, body:Message }
직렬화: Serde + Postcard
검사·경계: COBS( Postcard(Frame) || CRC32-LE ) || 0x00
전송: USB CDC-ACM 바이트 스트림
하위 출력: I2C0 / SPI0 / PIO+DMA / GPIO
```

`MAX_DECODED=512B`, `MAX_WIRE=520B`이며 조각난 USB 패킷·연속 프레임을 decoder에서 재조립한다. CRC는 CRC-32/ISO-HDLC다. USB CDC는 UART 전기 신호를 그대로 뜻하지 않는다. 세션·sequence의 최근 8개 중복 결과는 재응답하고 재실행하지 않으며 캐시 밖 오래된 요청은 거부한다. `Ack`는 수락, `Applied`는 보간 목표의 PWM 등 레지스터 반영이다. `commanded_cdeg`도 센서로 측정한 관절각이 아니다.

## 기술 슬라이드와 발표자 메모

### 15. Rust로 정책과 장치 실행을 분리했습니다

기술 01  /  SBC는 인식·기억·대화, MCU는 시간 제약이 있는 입출력을 담당합니다.

MA는 저장소의 Rust micro-architecture, 즉 역할별 독립 프로세스 구조로 설명합니다. Jetson Nano는 Linux와 Tokio에서 사용자 요청·기억·추론·미디어를 처리하고 Pico 2 W는 Rust/Embassy로 GPIO·I2C·SPI·PIO를 제어합니다. 무선 기능은 현재 Pico 펌웨어에서 사용하지 않습니다. 일반 목적 Linux를 강한 실시간 제어기로 가정하지 않습니다.

### 16. RTOS 관점에서 본 Rust·Embassy 태스크 구조

기술 02  /  Rust 1.90 · embassy-rp / executor 0.10 · Cortex-M33 단일 코어

이 펌웨어는 no_std/no_main이며 thread-mode executor를 사용합니다. main은 다섯 태스크를 spawn한 뒤 device_task를 await하므로 여섯 논리 실행 흐름입니다. usb_task, rx_task, tx_task, touch_task, safety_task가 분리됩니다. device_task가 PCA·눈·양손 LED 출력 I/O를 단독 소유합니다. 정적 태스크와 bounded Channel/Signal을 사용합니다. 같은 executor에서는 await 지점에서 협력적으로 진행하므로 긴 동기 연산이나 blocking I/O가 다른 태스크를 지연시킬 수 있습니다. 선점형 RTOS의 태스크 우선순위 보장으로 설명하지 않습니다. 출처: https://docs.embassy.dev/embassy-executor/0.10.0/cortex-m/index.html , https://embassy.dev/book/

### 17. 시간 제한과 정지는 별도 경로로 관리합니다

기술 03  /  아래 수치는 코드의 설정값이며 실제 정지 지연의 상한을 보증하지 않습니다.

제어 계층 두 곳의 lease를 구분합니다. Nano controller lease는 750ms이고 Pico wire lease는 1000ms입니다. USB 호스트는 약 200ms마다 KeepAlive를 보냅니다. 입력·safety 루프는 5ms, 출력 tick은 20ms, 상태 보고는 약 100ms입니다. I2C 요청 timeout은 40ms입니다. 올바른 version·CRC의 Stop을 수신하면 세션·sequence 입장 검사보다 먼저 OE를 HIGH로 하고 generation을 변경합니다. 출력 owner가 LED black·matrix blank/shutdown·PCA all-off를 정리합니다. device 진행 시각이 250ms 이상 오래되면 safety_task가 Stop을 요청하고 1초 hardware watchdog 급전을 멈추는 구조입니다. executor 자체가 막히면 safety_task도 즉시 실행될 수 없으므로 watchdog 고장 주입과 전기적 정지는 별도 검증입니다.

### 18. SBC MA는 7개의 독립 프로세스입니다

기술 04  /  같은 nano-runtime 실행 파일을 역할별로 실행하고 장치 소유권을 분리합니다.

초기 설계보다 실제 실행판과 소유권을 우선합니다. controllerd가 조용한 대기·Help·Stop·epoch·lease를 결정하고, picod가 USB 브리지 자식 하나를 소유합니다. camerad는 CSI 두 대, audiod는 USB 오디오 입출력을 독점합니다. visiond는 최신 프레임을 분석하고 OCR 후보를 냅니다. memoryd는 SQLite WAL과 확인된 메모를 관리합니다. dialogued는 공급자·ASR·TTS 연결과 비용·동의·취소를 처리합니다. GStreamer·SQLite·CUDA 네이티브 기능은 작은 C ABI로 연결하며 로컬 AI worker도 포함합니다. 모두 순수 Rust 드라이버로 다시 작성했다는 의미는 아닙니다. 설치판 picod의 내부 UDP는 private network namespace에 제한합니다.

**근거:** 근거: software/README.md / nano-runtime/src / deploy/300seconds-runtime@.service

### 19. 제어·영상·음성을 다른 경로로 전달합니다

기술 05  /  대용량 데이터가 정지·제어 메시지의 처리를 밀어내지 않도록 나눴습니다.

제어는 AF_UNIX SOCK_STREAM에서 4바이트 big-endian 길이와 JSON 본문을 사용하며 최대 64KiB입니다. 영상의 실제 구현은 POSIX mmap이 아닌 /run tmpfs의 3슬롯 파일, FRM1 header, nonblocking flock입니다. 최신 프레임을 고르며 generation과 500ms age를 검사하고 슬롯이 모두 사용 중이면 drop합니다. 분석용 출력은 320×240 NV12 약10fps이며 센서 720p30과 구분합니다. 음성은 별도 Unix stream에서 length+PCM1 header+48kHz mono S16LE로 전달합니다. PCM에는 epoch·sequence·timestamp가 있고 200ms age와 lease를 확인합니다. Stop 후 지난 epoch의 PCM을 거부합니다. zero-copy나 최종 shared-memory 설계 완료로 소개하지 않습니다. 출처: https://tokio.rs/tokio/tutorial/framing

**근거:** 근거: host-core/src/lib.rs, shm.rs / doc/software/소프트웨어_아키텍처_계획.md 0절

### 20. 통신 스택은 공통 타입에서 배선까지 연결됩니다

기술 06  /  no_std 공통 crate로 MCU·SBC의 메시지 타입과 codec을 공유합니다.

응용 메시지는 Hello·KeepAlive·Arm·SetPose·SetLight·SetEyes·Stop과 Ack·Outputs·Applied입니다. Frame의 version:u8/session:u64/seq:u32와 body를 Serde/Postcard로 직렬화하고 CRC-32/ISO-HDLC little-endian을 붙인 뒤 COBS와 0x00 delimiter를 씁니다. 최대 decoded 512B와 wire 520B이며 버퍼 초과 시 다음 delimiter까지 버린 뒤 복구합니다. USB CDC-ACM 바이트 스트림의 패킷 경계는 응용 프레임 경계가 아닙니다. 같은 session/seq는 최근 8개 중복 결과를 재응답하고 재실행하지 않으며 오래된 sequence는 거부합니다. Ack는 수락, Applied는 PWM 등 레지스터 적용이며 실제 관절각 측정은 아닙니다. 하단 값은 코드의 실제 bus 설정이고 부품 최대 정격이 아닙니다. PDF 근거: PCA9685 p.1~2, MAX7219 p.1, WS2812B V5 p.1,4.

**근거:** 근거: pico-device-protocol / firmware src/main.rs / PCA9685·MAX7219·WS2812B PDF

### 21. 도움 한 번을 턴·권한·epoch로 묶습니다

기술 07  /  모델의 응답과 실제 출력 권한 사이에 Rust 정책 검사를 둡니다.

명시적 Help에서 턴을 시작하고 관련 기억을 읽은 뒤 요청 범위만 모델에 전달합니다. OCR 후보는 사용자가 confirm-problem한 문장만 사용합니다. 외부 전송은 동의를 확인하고 ledger를 먼저 예약합니다. 모델 출력은 action 후보이며 epoch·age·정지 상태·요청 여부를 확인하는 정책 gate를 통과해야 합니다. 현재 confidence 0.85는 검증·보정된 확률이 아닌 코드 후보 기준입니다. Stop이나 정정으로 epoch를 바꾸면 늦은 HTTP 응답과 예전 PCM을 거부하고 완료 시 quiet로 복귀합니다. Stop이 외부 공급자 과금 취소를 보증하지 않습니다.

**근거:** 근거: nano-runtime/src/turns.rs, policy.rs / host-core/src/decision.rs

### 22. 단계별 구현은 작은 성공에서 통합으로 이어집니다

기술 08  /  각 단계의 통과 근거를 남기고 다음 계층으로 연결했습니다.

단계표의 초기 계획과 후속 구현 기록을 합쳐 설명합니다. A에서 no_std 타입·codec·디바운스·보정 같은 순수 로직을 PC에서 검사합니다. B에서 Pico 장치별 유한 시험과 Stop, USB 계약을 연결합니다. C에서 Nano OS/native library·권한·카메라·오디오를 독립 확인합니다. D에서 7개 프로세스와 IPC·epoch·lease를 통합합니다. E에서 실제 외부 생성·TTS, OCR 후보·확인된 기억을 묶습니다. F는 전원·기구·장애·사용자 시나리오의 반복 검증입니다. A~E는 일부 또는 기록된 통과 근거가 있고 F의 전 항목이 완료됐다는 주장은 하지 않습니다.

**근거:** 근거: 개발_단계_및_점검표.md / firmware·protocol·software / 실제 RUN·검증 JSON

### 23. 빌드·배포·복구 절차를 고정했습니다

기술 09  /  Nano/Linux 실행 예시. 이번 자료 작성 중 실행하지 않았습니다.

Pico는 thumbv8m.main-none-eabihf release ELF를 RP2350 Arm secure UF2로 변환합니다. --check는 준비 상태 확인이고 쓰기 작업이 아닙니다. 실제 업로드는 대상 보드와 기존 flash 백업 확인 후 수행하고 readback과 재연결 Status로 검증합니다. SBC는 고정 Cargo.lock과 보드의 GStreamer·SQLite·CUDA에 링크해 빌드합니다. /opt의 root 소유 바이너리와 /run·/var/lib의 실행 데이터를 나눕니다. systemd는 boarddash·udev 그룹·0660 Unix socket을 사용하고 runtime target을 수동 시작합니다. 설치만으로 새로운 firmware를 쓰거나 구동하지 않습니다. Git pull도 /opt 설치판이나 Pico flash를 자동 갱신하지 않습니다.

**근거:** 근거: firmware/build-pico-device.sh, flash-pico.sh / software/README.md, install.sh

### 24. 구현 근거는 테스트의 층별로 확인합니다

기술 10  /  아래 수치는 저장소에 남긴 해당 실행판의 검증 기록입니다.

기록된 release의 순수 로직·회귀 합계는 60개입니다. 34개 계약·취소·기억·구동 검사는 실제 Pico/audio와 합성 HTTP 23회를 포함하고 외부 생성은 0회입니다. 20개 장치 runtime 검사는 실제 CSI·CUDA/TensorRT·PCM·SQLite·lease·Stop 경로를 포함합니다. 14개 설치판 검사는 crop OCR·카메라 재시작 generation·Pico/audio 강제 종료·수동 복구·3분 quiet를 포함합니다. 집합이 겹치므로 합쳐서 독립 테스트 총수로 표현하지 않습니다. 이것이 장기 무고장·학습 효과·물리 위치·AEC·동시 발화 검증을 뜻하지도 않습니다. full-acoustics.json의 candidate_pass=false를 별도로 표기합니다.

**근거:** 근거: 전체기능_구현과_운영.md / full-runtime-hardware, full-features, full-systemd JSON

### 25. 다음 기술 단계는 안정성과 실사용 검증입니다

기술 11  /  구현 성공과 장시간·실환경 성능을 따로 판정합니다.

AEC chirp 시험은 충분한 excitation이 없어 candidate_pass=false였고 실제 음성 끼어들기는 비활성입니다. controller 종료 뒤 정지 상태 관측은 단일 표본이며 커널 전체 hang 또는 물리 관절 정지의 상한이 아닙니다. 저전압과 OC 경고가 반복돼 전원 안정성은 합격 처리하지 않습니다. 동일 5W 구성에서 높은 CPU 부하와 웹 MJPEG 전달 약11fps를 관찰한 기록을 센서 30fps와 구분합니다. 다음은 안정된 전원·각축 보정·watchdog starvation/USB 분리/리셋의 체계적인 고장 주입, 한국어·OCR·수학 힌트 정확도, 학생 요청·대기 경험을 반복 측정하는 일입니다.

**근거:** 근거: full-acoustics.json / 전체기능_구현과_운영.md / 최신 카메라·저전압 진단

## 재현 절차의 순서

1. **순수 로직:** 공통 protocol·터치·보정·codec을 PC에서 검사하고 고정 toolchain/lockfile을 보관한다.
2. **MCU 벤치:** 장치별 유한 시험과 Stop을 확인한 뒤 USB 요청·응답·세션·중복·단절을 결합한다.
3. **SBC 기초:** 보드 manifest·권한·네이티브 라이브러리·카메라·오디오를 단독 검증한다.
4. **MA 통합:** 7개 프로세스와 제어·프레임·PCM 계약, freshness·epoch·lease를 연결한다.
5. **학습 기능:** 동의한 요청의 대화·TTS·OCR 확인·목표·기억을 한 턴으로 통합한다.
6. **실사용 검증:** 전원·기구 보정·장애 복구·한국어/교재 정확도·자율학습 경험을 반복 확인한다.

이번 작업에서는 자료만 편집했다. Pico flash·서비스 전환·새 카메라 촬영·외부 AI 추론 호출은 수행하지 않았다. 배포 예시의 `flash-pico.sh --check`는 준비 확인이며 flash 기록이 아니다. 실제 기록은 대상 확인·백업·Stop 후 수행하고 readback·재연결 Status를 확인하는 기존 절차를 따른다.
